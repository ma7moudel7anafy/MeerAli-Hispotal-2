## 1. Executive Summary – ملخص تنفيذي محدث

يهدف هذا التقرير المحدث إلى وضع المخطط الهندسي الدقيق والنهائي لتحويل نظام **MeetAli-Hospital 2** من معمارية هجينة غير متماثلة (تعتمد في أكثر من 85% من وظائفها على `LocalStorage` بالمتصفح مع 7 مسارات خادم بدائية غير آمنة) إلى **معمارية خادم مركزي محلي موحد ومحصن (Local Central Server Architecture)**.

### المبادئ الهندسية الحاكمة في النسخة المحدثة:
1. **الخادم المضيف ونطاق الشبكة:** يرتبط الخادم حصريًا على العنوان المحلي `127.0.0.1` والمنفذ `3000`. لا يدّعي النظام دعم شبكة محلية متعددة الأجهزة (LAN Multi-device) في هذه المرحلة؛ حيث تتطلب بيئة LAN ضوابط حماية إضافية (مثل HTTPS محلي، CORS مقيد، إدارة شهادات، وتأمين منافذ) يتم تأجيلها لمرحلة لاحقة بعد استقرار الخادم الموحد.
2. **محرك تخزين ذري منضبط (JsonDatabaseEngine):**
   - الحفاظ على نسخة حديثة ومفهرسة في ذاكرة الخادم (In-Memory Database Instance).
   - تنفيذ جميع عمليات الكتابة عبر **طابور تسلسلي مركزي موحد (Single Centralized Write Queue / Mutex)** لمنع تداخل العمليات المتزامنة (Race Conditions).
   - **قاعدة النزاهة الصارمة:** عدم تعديل النسخة الأساسية في الذاكرة نهائيًا إلا بعد نجاح عملية الكتابة على القرص وتأكيدها.
   - التحقق من صحة البيانات والعلاقات والقيود قبل فتح أي عملية كتابة.
   - الكتابة عبر ملف مؤقت (`hospital_db.json.tmp`) ثم استبدال ذري على مستوى نظام التشغيل (`fs.renameSync`).
   - عدم إرسال استجابة نجاح (HTTP 200/201) للعميل، وعدم نشر أحداث SSE اللحظية، إلا **بعد اكتمال الحفظ بنجاح تام على القرص**.
3. **سياسة صارمة لمنع التلف وإيقاف الاستبدال التلقائي:**
   - **إلغاء تام** لآلية النسخ التلقائي لملف البذرة `initial_seed.json` عند فشل قراءة ملف البيانات.
   - عند اكتشاف أي تلف في JSON: يتم تجميد الكتابة فورًا، عزل الملف التالف في مجلد خاص دون مسه، دخول الخادم في وضع الاسترداد الآمن (Recovery Mode)، والبحث عن أحدث نسخة احتياطية صالحة لعرضها على المسؤول وطلب موافقة صريحة قبل أي استعادة.
4. **أمان ومصادقة حقيقية من جهة الخادم (Server-Side Auth & RBAC):**
   - التخلي نهائيًا عن الاعتماد على ترويسات العميل غير الموثوقة (`x-staff-id`, `x-staff-role`).
   - إنشاء جلسات عمل مشفرة وموثوقة يتحقق منها Express في كل طلب حساس (Cashier, Refunds, Price edits, Staff management, Backups).
5. **سياسة نسخ احتياطي موحدة ومنضبطة:**
   - نسخة تلقائية دورية كل 60 دقيقة.
   - نسخة إلزامية قبل أي استعادة أو إعادة تهيئة أو ترقية لبنية البيانات.
   - الاحتفاظ بآخر 48 نسخة على الأقل، مع الإبقاء على كافة النسخ التي لم يتجاوز عمرها 7 أيام.
   - دعم إنشاء نسخ يدوية فورية عند طلب المسؤول، مع التحقق من سلامة النسخة وقابليتها للاستعادة.
6. **واقعية الحل المعماري:**
   - توثيق صريح بأن استخدام ملف JSON محلي هو حل هندسي انتقالي مرحلي لتبسيط التشغيل المحلي بدون تبعيات خارجية، ولكنه **ليس قاعدة بيانات علائقية كاملة (ACID RDBMS)** للتعامل مع آلاف المعاملات المتزامنة في الثانية.

## 3. Storage Engine Deep-Dive – تصميم محرك التخزين المركزي المنضبط

### 3.1 هيكل ودورة حياة `JsonDatabaseEngine`
لمعالجة مخاطر تلف البيانات وتداخل العمليات، يُصمم المحرك وفق الخوارزمية التالية:

```
[استقبال طلب كتابة (Write Request)]
             │
             ▼
[1. التحقق المسبق من صحة البيانات والعلاقات (Validation)]
 ├── التحقق من الحقول الإلزامية والأنواع
 └── التحقق من الكيانات المرتبطة (Foreign Keys: المريض، الطبيب، الخدمة...)
             │
             ├─ [غير صالح] ──► رفض فوري وإرجاع خطأ 400 Bad Request
             ▼ [صالح]
[2. الدخول في طابور الكتابة المركزي (Write Queue / Mutex Lock)]
             │
             ▼
[3. تجهيز الحالة المرشحة (Staging Candidate State)]
 (نسخ عميق للحالة الحالية في الذاكرة + تطبيق التعديل عليها في كائن مستقل)
             │
             ▼
[4. كتابة الحالة المرشحة في ملف مؤقت (Write to data/hospital_db.json.tmp)]
             │
             ├─ [فشل الكتابة (مساحة قرص، أذونات)] ──► إلغاء العملية، حذف .tmp،
             │                                         عدم المساس بالذاكرة، إرجاع خطأ 500
             ▼ [نجاح الكتابة في .tmp]
[5. الاستبدال الذري (fs.renameSync(tmp, hospital_db.json))]
 (عملية ذرية غير قابلة للتجزئة مدعومة من نظام التشغيل POSIX/Windows)
             │
             ├─ [فشل الاستبدال] ──► خطأ حرج، لا يتم تعديل الذاكرة، إرجاع خطأ 500
             ▼ [نجاح الاستبدال الذري على القرص]
[6. ترقية الحالة في الذاكرة (Commit to In-Memory Instance)]
 (النسخة الأساسية في الذاكرة تصبح مطابقة تماماً للملف على القرص)
             │
             ├──► [7. بث الحدث لحظياً عبر SSE للمشتركين]
             │
             └──► [8. إرسال استجابة النجاح HTTP Success (200/201) للعميل]
             │
             ▼
[9. تحرير قفل الطابور لمعالجة الطلب التالي (Release Queue Lock)]
```

### 3.2 سلوك الخادم عند انقطاع العملية أثناء الحفظ (Crash / Interruption Behavior)
1. **انقطاع أثناء كتابة `.tmp` (Power Outage / SIGKILL):**
   - الملف الأصلي `data/hospital_db.json` يظل سليمًا 100% ودون أي مساس.
   - الملف المؤقت `hospital_db.json.tmp` يظل كملف مهجور غير مكتمل.
   - عند إقلاع الخادم: يقوم المحرك تلقائيًا بفحص مجلد `data/` ومسح أي ملف `.tmp` متبقٍ بأمان.
2. **انقطاع أثناء تنفيذ `fs.renameSync`:**
   - نظام الملفات يضمن ذريّة (Atomicity) الأمر: إما أن يُستبدل الملف بالكامل أو يظل الملف القديم كاملًا. لا يمكن حدوث حالة ملف مشوه بحجم صفر بايت.
3. **معالجة فشل الكتابة (ENOSPC / EACCES):**
   - إذا امتلأ القرص أو تعذر الوصول، تلتقط الـ Queue الخطأ، وتُبقي النسخة السابقة في الذاكرة والقرص دون أي تلوث، ويتم إخطار المتصل بفشل العملية وسببها دون فقدان البيانات السابقة.

## 4. Disaster Recovery & Anti-Corruption Policy – سياسة التعامل مع تلف JSON

### 4.1 حظر الاستبدال الصامت بالبذرة الافتراضية
**قاعدة قطعية:** يُلغى نهائيًا الكود الموجود حاليًا في `server.ts` الذي يقوم بنسخ `initial_seed.json` عند فشل قراءة `hospital_db.json`.

### 4.2 بروتوكول معالجة التلف والاسترداد الآمن (Recovery Protocol)
عند تشغيل الخادم (`loadDatabaseOnStartup`):
```
[محاولة قراءة وتفسير data/hospital_db.json]
             │
             ├─ [قراءة ناجحة وصيغة سليمة] ──► تشغيل الخادم في الوضع الطبيعي Normal Mode
             │
             ▼ [فشل القراءة أو JSON تالف SyntaxError]
[1. إيقاف وتجميد كافة مسارات الكتابة (Disable All Write Routes)]
             │
             ▼
[2. عزل وحجر الملف التالف دون مسه أو حذفه]
 └── نقل الملف إلى: data/corrupted/hospital_db_corrupted_YYYYMMDD_HHMMSS.json
             │
             ▼
[3. الدخول في وضع الاسترداد الحرج (Recovery Mode)]
 ├── تفعيل مسار الفحص: GET /api/recovery/status
 ├── تفعيل مسار الاستعادة: POST /api/recovery/confirm-restore
 └── رفض أي طلبات تشغيلية أخرى برمز 503 Service Unavailable (System in Recovery)
             │
             ▼
[4. البحث والتحقق من النسخ الاحتياطية في data/backups/]
 ├── فحص النسخ بدءاً من الأحدث إلى الأقدم
 └── التحقق من سلامة البنية ومفاتيح الكيانات الإلزامية لكل نسخة
             │
             ▼
[5. تقديم واجهة الاسترداد للمسؤول (Admin Recovery Screen)]
 ├── عرض سبب الخطأ وتاريخ الملف المعزول
 ├── عرض قائمة النسخ السليمة المتاحة مع أوقاتها وعدد سجلاتها
 └── اشتراط إدخال كود تأكيد ومصادقة المدير (Admin PIN/Password)
             │
             ▼
[6. تنفيذ الاستعادة المعتمدة بعد الموافقة الصريحة]
 ├── إنشاء نسخة احتياطية من الملف المعزول في مجلد الحجر
 ├── نسخ ملف النسخة الاحتياطية المعتمدة ليصبح hospital_db.json
 └── إعادة قراءة البيانات وتفعيل الوضع الطبيعي Normal Mode
```

## 5. Server-Side Authentication & RBAC – إعادة تصميم المصادقة والصلاحيات

### 5.1 إسقاط الترويسات الزائفة واعتماد جلسات الخادم الموثوقة
- الترويسات الحالية (`x-staff-id`, `x-staff-role`) هي بيانات يرسلها المتصفح بسهولة ويمكن لأي مستخدم تعديلها في أدوات المطور (DevTools) لانتحال شخصية مدير.
- **التصميم الجديد:**
  1. يقوم المستخدم بتسجيل الدخول عبر مسار رسمي `POST /api/auth/login` بإرسال اسم المستخدم ورمز الدخول (PIN / Password).
  2. يتحقق الخادم من وجود الموظف في مصفوفة `staff` داخل JSON، ومطابقة الرمز المشفر، وكون حسابه نشطًا (`is_active: true`).
  3. ينشئ الخادم جلسة موثوقة في الذاكرة (Server-Side Session Store) تحتوي على:
     - `sessionId`: معرف جلسة عشوائي مشفر غير قابل للتنبؤ (Crypto UUID).
     - `staffId`: معرف الموظف المحقق.
     - `role`: الرتبة الفعلية المسجلة بالخادم (وليس المرسلة من العميل).
     - `name`: اسم الموظف.
     - `createdAt` و `expiresAt`: تاريخ انتهاء الجلسة (افتراضيًا 12 ساعة وردية).
  4. يُعاد `token` للعميل، ليُرسل في الترويسة القياسية `Authorization: Bearer <token>`.
  5. تقوم طبقة وسيطة بالخادم (`requireAuth` & `requireRole`) بفحص الجلسة واستخراج الرتبة من ذاكرة الخادم قبل السماح بتمرير الطلب.

### 5.2 مصفوفة الصلاحيات على مستوى واجهات البرمجة (API RBAC Matrix)
| المجال ومسارات الـ API | الرتب المسموح لها | القيود والشروط البرمجية بالخادم |
| :--- | :--- | :--- |
| **تسجيل الدخول والاستعلام:** `/api/auth/*` | الجميع (مفتوح للتوثيق) | تحديد عدد المحاولات الفاشلة (Rate Limiting). |
| **إدارة الموظفين:** `/api/staff` (CRUD) | `admin` فقط | منع حذف الحساب الإداري الرئيسي. |
| **إدارة العيادات والأطباء والأسعار:** `/api/specialties`, `/api/doctors` | `admin` فقط | منع حذف تخصص أو طبيب مرتبط بكشوفات سابقة. |
| **تسجيل المرضى وحجز الكشوفات:** `/api/patients`, `/api/visits` | `admin`, `reception` | التحقق من صحة الهاتف وتوليد الرقم الذري. |

## 6. Unified Backup & Snapshot Policy – سياسة النسخ الاحتياطي الموحدة

### 6.1 فض التعارض وتوحيد القواعد
تم حل التعارض السابق بين "الاحتفاظ بـ 10 نسخ" وبين "الاحتفاظ بنسخ لمدة 7 أيام" عبر اعتماد السياسة الهندسية المزدوجة التالية:

1. **التردد التلقائي:**
   - إنشاء نسخة احتياطية تلقائية كل **60 دقيقة** أثناء تشغيل الخادم.
   - إنشاء نسخة فورية قبل تنفيذ أي عملية إعادة ضبط (`/api/reset-demo`).
   - إنشاء نسخة فورية قبل أي عملية استعادة لبيانات سابقة (`/api/backup/restore`).
   - إنشاء نسخة فورية قبل ترقية بنية كائن البيانات (Schema Migration).
2. **النسخ اليدوي:**
   - توفير زر "إنشاء نسخة احتياطية فورية الآن" للمدير في لوحة التحكم (`POST /api/backup/create`).
3. **قاعدة الاستبقاء المزدوجة (Dual Retention Policy):**
   - **الحد الأدنى العددي:** الاحتفاظ دائمًا بآخر **48 نسخة احتياطية** على الأقل (تغطي يومين كاملين من النسخ الساعي حتى في حال توقف العمل).
   - **الحد الزمني:** الإبقاء على كافة النسخ الاحتياطية التي تم إنشاؤها خلال آخر **7 أيام**.
   - لا يتم حذف أي نسخة إلا إذا تجاوزت 7 أيام **وكان إجمالي النسخ المتبقية أكثر من 48 نسخة**.
4. **التحقق من سلامة النسخة وقابليتها للاستعادة:**
   - بعد كتابة النسخة الاحتياطية في `data/backups/hospital_db_YYYY-MM-DD_HH-mm-ss.json`، يقوم المحرك بقراءتها فورًا والتأكد من أنها تمثل كائن JSON صالح، وأنه يحتوي على المفاتيح الإلزامية الـ 14.
5. **التعامل مع فشل إنشاء النسخة الاحتياطية:**
   - إذا فشل إنشاء النسخة الاحتياطية (بسبب نقص المساحة أو أذونات القرص): يتم تسجيل خطأ حرج (CRITICAL_ALERT) في سجل التدقيق ومخرجات الخادم، مع إرسال تحذير للوحة الإدارة. **لا يتم تعطيل مسارات الكشف الطبي العاجلة**، ولكن يُمنع تنفيذ عمليات الإدارة والتهيئة الحساسة لحين حل مشكلة التخزين.

## 8. Complete Reconciled REST API Specifications – جرد وتوثيق الـ 45 مسارًا

سيحتوي الخادم المركزي على **45 مسار REST API محددًا ومحكمًا بدقة**، بالإضافة إلى قناة أحداث SSE:

### 8.1 مسارات التوثيق والجلسات (Authentication API - 3 مسارات)
1. `POST /api/auth/login` — تسجيل دخول الموظف والتحقق من كلمة المرور/الرمز وإصدار معرف الجلسة.
2. `POST /api/auth/logout` — إلغاء وتدمير الجلسة من ذاكرة الخادم.
3. `GET /api/auth/me` — استرجاع بيانات الجلسة الحالية والرتبة المحققة للموظف.

### 8.2 مسارات المرضى (Patients API - 3 مسارات)
4. `GET /api/patients?search=...` — جلب وبحث المرضى بالاسم أو الهاتف أو الرقم التسلسلي.
5. `POST /api/patients` — تسجيل مريض جديد وتوليد الرقم الذري `P-YYYY-XXXXX` والتحقق من عدم تكرار الهاتف.
6. `PUT /api/patients/:id` — تعديل بيانات المريض ومزامنة اسمه وهاتفه تلقائيًا في كافة زياراته السابقة.

### 8.3 مسارات الكشوفات والزيارات (Visits & Clinical API - 6 مسارات)
7. `GET /api/visits?date=...&doctorId=...&patientId=...&status=...` — جلب وفلترة الزيارات.
8. `POST /api/visits` — حجز كشف جديد مع التحقق من تخصص الطبيب وتطبيق جدول الأسعار وحساب الأولوية وتوليد رقم الزيارة اليومي.
9. `PUT /api/visits/:id/status` — تحديث حالة الزيارة (`registered`, `attended`, `in_consultation`, `completed`, `cancelled`).
10. `POST /api/visits/:id/pay` — تحصيل رسوم الكشف بالخزينة وإصدار إيصال السداد الذري `REC-YYYY-XXXXX` ومنع التكرار.
11. `POST /api/visits/:id/refund` — استرداد الرسوم وتوثيق سبب الإلغاء وخصم المبلغ من رصيد الخزينة وتسجيله بالتدقيق.
12. `PUT /api/visits/:id/diagnosis` — اعتماد الكشف الطبي وحفظ الأعراض والتشخيص والروشتة (يُشترط أن تكون الزيارة مدفوعة).

### 8.4 مسارات المعمل والأشعة والربط السريري (Diagnostics API - 8 مسارات)
13. `GET /api/diagnostics/services` — استرجاع دليل خدمات الفحوصات والتحاليل.
14. `POST /api/diagnostics/services` — إضافة خدمة فحص أو تحليل جديدة (للمدير فقط).
15. `PUT /api/diagnostics/services/:id` — تعديل سعر خدمة أو تعليمات التحضير أو حالتها (للمدير فقط).
16. `DELETE /api/diagnostics/services/:id` — إيقاف أو حذف خدمة فحص.
17. `GET /api/diagnostics/orders?department=...&status=...` — جلب طابور طلبات الفحوصات للفنيين.
18. `POST /api/diagnostics/orders` — إنشاء طلب فحص جديد (سواء محول من عيادة أو حجز استقبال) وإدراجه في دورة الخزينة.
19. `PUT /api/diagnostics/orders/:id/status` — تحديث حالة طلب الفحص (`waiting`, `in_progress`, `result_ready`, `delivered`).
20. `PUT /api/diagnostics/orders/:id/results` — **(مسار الربط السريري المفقود)** تسجيل نتائج التحاليل والتقارير الإشعاعية، مع قيام الخادم تلقائيًا بحقن النتيجة في سجل الزيارة الأصلية للمريض لتمكين الطبيب من مراجعتها فورًا.

### 8.5 مسارات الخزينة والوردية والماليات (Revenue & Cashier API - 3 مسارات)
21. `GET /api/revenue/summary?date=...` — احتساب الإيرادات اليومية وتوزيعها (كاش، إلكتروني، إعفاءات، مستردات) **مجمعة بدقة من كشوفات العيادات وخدمات المعمل والأشعة معًا**.
22. `GET /api/revenue/shift-float?date=...` — قراءة عهدة الفكة الافتتاحية لليوم.
23. `POST /api/revenue/shift-float` — تسجيل وتعديل عهدة بداية الوردية مع حفظها في ملف JSON المركزي.

### 8.6 مسارات التخصصات والأطباء والمواعيد والحضور (Clinics & Attendance API - 10 مسارات)
24. `GET /api/specialties` — استرجاع كافة التخصصات والعيادات.
25. `POST /api/specialties` — إضافة تخصص جديد (مدير فقط).
26. `PUT /api/specialties/:id` — تعديل بيانات تخصص (مدير فقط).
27. `DELETE /api/specialties/:id` — إيقاف تخصص (مع منع الحذف عند وجود أطباء مرتبطين به).
28. `GET /api/doctors` — استرجاع قائمة الأطباء وتفاصيل أسعارهم.
29. `POST /api/doctors` — إضافة طبيب وتحديد أسعار الكشف والاستشارة (مدير فقط).
30. `PUT /api/doctors/:id` — تعديل بيانات الطبيب وأسعاره (مدير فقط).
31. `DELETE /api/doctors/:id` — إيقاف أو حذف طبيب (مدير فقط).
32. `GET /api/schedules?doctorId=...` — استرجاع جداول المواعيد الأسبوعية للأطباء.
33. `POST /api/schedules` — ضبط وتحديث مواعيد عمل الطبيب.

### 8.7 مسار الحضور اليومي للأطباء (Doctor Attendance API - مساران)
34. `GET /api/attendance?date=...` — جلب سجل حضور الأطباء لليوم المحدد.
35. `POST /api/attendance` — تسجيل وتحديث حالة حضور الطبيب (حاضر، متأخر، معتذر) مع حفظ الملاحظات الإدارية.

### 8.8 مسارات طاقم العمل والرقابة والبروتوكولات (Staff, Audit & Presets API - 6 مسارات)
36. `GET /api/staff` — استرجاع حسابات الموظفين (مدير فقط).
37. `POST /api/staff` — إنشاء حساب موظف وتحديد رتبته وصلاحياته (مدير فقط).
38. `PUT /api/staff/:id` — تعديل بيانات الحساب أو تجميده (مدير فقط).
39. `GET /api/audit?limit=...` — استرجاع سجل التدقيق والرقابة الأمني (مدير فقط).
40. `GET /api/presets/clinical?specialtyId=...` — جلب بروتوكولات الأقسام ومفضلات الأطباء.
41. `PUT /api/presets/clinical/:specialtyId` — تحديث البروتوكولات السريرية للتخصص.

### 8.9 مسارات النسخ الاحتياطي وإعادة الضبط والاسترداد (Backup, Reset & Recovery API - 5 مسارات)
42. `POST /api/backup/create` — إنشاء نسخة احتياطية فورية على الخادم مع التحقق من سلامتها.
43. `GET /api/backup/list` — استعراض قائمة النسخ الاحتياطية المتوفرة وتواريخها وأحجامها.
44. `POST /api/backup/restore` — استعادة النظام من نسخة احتياطية محددة مع طلب تأكيد المدير وأخذ نسخة وقائية قبل التنفيذ.
45. `POST /api/reset-demo` — إعادة تهيئة النظام إلى البذرة الافتراضية النظيفة (مقيدة بطلب تأكيد صريح: `{ confirm: "RESET_MOCK_DATA" }` مع إنشاء نسخة احتياطية مسبقة).

### 8.10 مسارات النظام الحيوية والبث اللحظي
- `GET /api/recovery/status` — استعلام حالة الخادم (طبيعي / وضع استرداد حرج).
- `GET /api/events` — قناة بث Server-Sent Events (SSE) اللحظية لإشعار كافة الشاشات بالتحديثات **بعد نجاح حفظها على القرص فقط**.

*(المجموع الدقيق والمحقق: 45 مسار REST API + مسار فحص الاسترداد + مسار SSE).*

## 10. Robust Acceptance Testing Suite – اختبارات القبول المحدثة والمستقلة

تمت صياغة اختبارات القبول بحيث تكون **ديناميكية ومستقلة تمامًا عن أي أرقام أو سجلات ثابتة**:

### 1. اختبار التزامن وتوليد الأرقام المتسلسلة (Concurrent Sequence Test)
- **الإجراء:** إرسال 5 طلبات تسجيل مرضى متزامنة في نفس الجزء من الثانية عبر استدعاءات متوازية (`Promise.all`).
- **المعيار الحاكم للنجاح:**
  - تسجيل كافة المرضى الـ 5 بنجاح تام دون فقدان أي سجل.
  - حصول كل مريض على رقم فريد تصاعدي غير متكرر مطلقًا.
  - عدم حدوث أي تضارب (Collision) في عداد `counters.patient_sequence`.

### 2. اختبار تداخل عمليات الكتابة وعدم فقدان البيانات (Lost Update Prevention Test)
- **الإجراء:** إرسال عمليتي تعديل في نفس اللحظة (مثل: تحديث كشف مريض وفي نفس الوقت تسجيل حضور طبيب).
- **المعيار الحاكم للنجاح:** مرور العمليتين عبر الـ Write Queue بالتسلسل، وظهور أثر كلا التعديلين معًا في ملف JSON، وعدم قيام العملية الثانية بإلغاء أو محو بيانات العملية الأولى.

### 3. اختبار محاكاة فشل الكتابة على القرص (Simulated Disk Write Failure Test)
- **الإجراء:** محاكاة تعذر الكتابة (مثل حجب أذونات الكتابة مؤقتًا عن الملف أو امتلاء مساحة القرص).
- **المعيار الحاكم للنجاح:**
  - رفض الطلب مع إرجاع استجابة خطأ واضحة (500 Internal Error) للعميل.
  - احتفاظ النسخة الأساسية في الذاكرة بحالتها الأصلية السابقة دون أي تلوث.
  - سلامة ملف `hospital_db.json` الأصلي على القرص وعدم مساسه.

### 4. اختبار اكتشاف تلف JSON والدخول في وضع الاسترداد (JSON Corruption & Recovery Test)
- **الإجراء:** كتابة محتوى غير صالح (Corrupted String) في ملف `hospital_db.json` وإعادة تشغيل الخادم.
- **المعيار الحاكم للنجاح:**
  - رفض الخادم القاطع لاستبدال الملف تلقائيًا بملف `initial_seed.json`.
  - نقل الملف المشوه فورًا إلى مجلد `data/corrupted/`.
  - دخول الخادم في وضع الاسترداد الحرج (Recovery Mode) ورفض عمليات الحفظ العادية.
  - منع الاستعادة إلا بعد مصادقة المدير وتقديم موافقة صريحة.

### 5. اختبار النزاهة المالية والفصل بين النقدية والإعفاءات (Financial Reconciliation Test)
- **الإجراء:**
  1. تسجيل عهدة بداية وردية بقيمة متغيرة ($X).
  2. حجز كشف مدفوع نقدًا بقيمة ($Y).
  3. حجز كشف معفى 100% (حالة اجتماعية) بقيمة اسمية ($Z).
  4. تسجيل خدمة تحليل معمل نقدًا بقيمة ($W).
- **المعيار الحاكم للنجاح:**
  - الإيراد الفعلي المحصل بالخزينة يطابق تمامًا: `X + Y + W`.
  - عدم احتساب مبلغ الإعفاء `Z` ضمن النقدية الفعلية بالدرج، وتوثيقه في بند منفصل كـ "دعم وإعفاءات".
  - تطابق تام بين تقرير الخزينة والنقدية الفعلية.

### 6. اختبار منع التحصيل المزدوج وصحة الاسترداد (Payment & Refund Integrity Test)
- **الإجراء:**
  1. محاولة استدعاء `/api/visits/:id/pay` مرتين متتاليتين لنفس الزيارة.
  2. تنفيذ استرداد مالي `/api/visits/:id/refund` لزيارة مسددة.
- **المعيار الحاكم للنجاح:**
  - رفض محاولة السداد الثانية برمز خطأ (400 Already Paid).
  - خصم المبلغ المسترد بدقة من تقرير النقدية اليومية، وتوثيق سبب الإلغاء ورقم الإيصال في سجل التدقيق الأمني.

### 7. اختبار أمان الجلسات ومنع انتحال الصلاحيات (Security & Anti-Spoofing Test)
- **الإجراء:**
  1. إرسال طلب حذف طبيب أو تعديل أسعار مع إرسال الترويسة المزيفة `x-staff-role: admin` بدون جلسة مصادقة صالحة.
  2. إرسال طلب باستخدام جلسة موظف استقبال لاسترداد مبلغ مالي مقيد بالمدير.
- **المعيار الحاكم للنجاح:**
  - رفض الطلب الأول فورًا برمز (401 Unauthorized) لعدم وجود جلسة محققة بالخادم.
  - رفض الطلب الثاني برمز (403 Forbidden) لعدم مطابقة رتبة الجلسة المحفوظة بالخادم لصلاحيات العملية.

### 8. اختبار استقلال النظام التام عن LocalStorage (Zero-LocalStorage Independence Test)
- **الإجراء:**
  1. إجراء سلسلة عمليات (تسجيل مرضى، كشوفات، نتائج معامل، وسداد).
  2. مسح كامل بيانات التخزين المحلي للمتصفح بالكامل (Clear LocalStorage).
  3. إعادة تحميل الصفحة.
- **المعيار الحاكم للنجاح:**
  - ظهور كافة البيانات والزيارات والأطباء والنتائج المسجلة فورًا ودون أي نقص.
  - استمرار العمليات التشغيلية دون أي خطأ.

### 9. اختبار ثبات البيانات عند إعادة تشغيل الخادم (Server Restart Persistence Test)
- **الإجراء:** تسجيل عمليات جديدة ثم إيقاف عملية خادم Node.js بالكامل (`kill`) وإعادة تشغيلها مجددًا.
- **المعيار الحاكم للنجاح:** قراءة كافة البيانات المضافة حديثًا من ملف `hospital_db.json` بنسبة 100% دون فقدان أي حرف.

### 10. اختبار البناء والترجمة النظيفة (Clean Build & Lint Test)
- **المعيار الحاكم للنجاح:**
  - انتهاء أمر `npm run lint` بنجاح كامل وبدون أي خطأ (`0 errors, exit code 0`).
  - انتهاء أمر `npm run build` بنجاح وإنتاج الحزمة التشغيلية النهائية دون أي تحذيرات كاسرة.

## 11. Architectural Note & Realistic Boundaries – ملاحظة معمارية وحدود التشغيل

يجب توثيق الآتي بوضوح هندسي تام:
1. **طبيعة محرك JSON:** إن استخدام ملف JSON مركزي محمي بالكتابة الذرية وطابور العمليات والنسخ الاحتياطي الساعي هو **حل هندسي ممتاز ومثالي للمرحلة الحالية** ولمتطلبات المستشفى المحلي في وضع عدم الاتصال (Offline Local Operation)، حيث يوفر البساطة والسرعة وسهولة النقل والصيانة بدون أي تبعيات لتثبيت خوادم قواعد بيانات خارجية.
2. **حدود التحمل والترقية المستقبلية:** هذا المحرك ليس قاعدة بيانات علائقية كاملة (ACID RDBMS). عندما يتوسع النظام مستقبلاً ليعمل عبر شبكة محلية ضخمة بعشرات الأجهزة المتزامنة ومئات الآلاف من السجلات، فإن المسار الطبيعي حينها سيكون ترقية طبقة التخزين في `JsonDatabaseEngine` لترتبط بمحرك قاعدة بيانات علائقية حقيقية (مثل PostgreSQL أو SQLite أو Supabase). وبما أننا وضعنا واجهات الـ REST API وعميل الـ API الموحد كطبقة عازلة، فإن هذه الترقية المستقبلية ستتم في طبقة الخادم دون الحاجة لتعديل شاشات واجهة المستخدم.
